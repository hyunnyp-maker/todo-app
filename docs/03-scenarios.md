## 0. 답변에서 드러난 두 가지

이번 Phase의 답변은 앞선 가정 하나를 뒤집었고, 위험 하나를 드러냈다.

### 뒤집힌 가정 — 카테고리 관리는 "설정 깊숙이"가 아니다

Phase 2까지는 카테고리를 **한 번 세팅하고 안 건드리는 것**으로 봤다.
답변은 **S4-c: 자주 손댐 — 색 바꾸는 재미로**였다.

이건 단순한 위치 조정이 아니다. **색 고르기가 이 앱의 즐거움 중 하나**라는 뜻이고,
그렇다면 팔레트는 "기능"이 아니라 **콘텐츠**다. Phase 5(디자인)의 무게중심이 바뀐다.

### 드러난 위험 — 이탈 원인 1순위가 "입력 마찰"

**S5-b: 적는 게 귀찮아짐 — 다른 데 적는 게 더 빠름.**

성취감 부족(c)도, 밀린 할일(a)도 아니었다. **입력 속도 그 자체**가 생명줄이다.
Phase 2의 T1("3초 안에 적기")은 이제 여러 긴장점 중 하나가 아니라 **최우선 원칙**이다.

> 이 앱이 실패한다면 기능이 부족해서가 아니라, **적는 데 5초가 걸려서**다.

## S1. 회의 끝나고 걸어 나오며 — 최악 조건 입력

### Context

- **자세**: 서서, 걸으면서. **한 손**. 다른 손엔 노트북
- **시간**: 10초. 자리에 앉으면 잊는다
- **머릿속**: "어린이집 준비물"
- **네트워크**: 사무실 와이파이, 양호

### Flow

```
① 휴대폰 꺼내 앱 실행 (홈 화면에 아이콘 / PWA)
② 화면 하단 [+] — 엄지가 닿는 위치
③ 제목 입력창에 커서가 이미 있음 → "어린이집 준비물"
④ 카테고리: 마지막에 쓴 게 이미 선택돼 있음 (가족)
⑤ 날짜: 오늘로 이미 채워져 있음
⑥ [저장]
```

**탭 수: 3회** (앱 아이콘 → + → 저장) + 타이핑

### 인사이트

- **④⑤가 비어 있으면 이 시나리오는 실패한다.** 걸으면서 드롭다운을 두 번 여는 건 불가능하다
- 기본값이 틀렸을 때 고치는 비용 < 매번 고르는 비용. **틀린 기본값이 빈 값보다 낫다**
- [+] 버튼은 **하단 고정**. 상단 우측(전통적 위치)은 한 손 엄지가 닿지 않는다
- 저장 후에는 **입력 화면이 닫히고 원래 화면으로.** 확인 토스트도 사치다

## S2. 아침 출근길 지하철 — 첫 화면 기본 상태

### Context

- **자세**: 서서 손잡이. 한 손
- **질문**: "오늘 뭐 있지?"
- **네트워크**: ⚠️ **지하철. 끊겼다 붙었다 한다**

### Flow

```
① 앱 실행
② 아무 조작 없이 화면에 이미 있어야 할 것:
   ┌─────────────────────┐
   │  2026년 8월          │
   │  일 월 화 수 목 금 토  │
   │           ●●   ●    │  ← 오늘 셀 강조
   │  ...                │
   ├─────────────────────┤
   │  8월 3일 (오늘)      │
   │  ▢ 주간보고 초안  직장 │
   │  ▢ 어린이집 준비물 가족 │
   │  ▢ 30분 걷기  개인 12/31│
   └─────────────────────┘
③ 스크롤 없이 오늘 할일이 보임
④ (선택) 하나 체크
```

### 인사이트

- **앱을 열면 항상 "오늘"이다.** 마지막으로 보던 날짜를 기억하지 않는다. 어제 4월을 보다 껐어도 오늘 열면 오늘
- 달력과 오늘 리스트가 **한 화면에 동시에** 있어야 한다. 스크롤해야 리스트가 나오면 이 시나리오가 깨진다
  - → 375px 세로 공간에서 달력은 **압축**돼야 한다. 셀 안 점(dot) 방식이 맞는 이유
- 지속형은 "12/31일"이 아니라 **오늘 했는지**가 먼저 보여야 한다
- ⚠️ **네트워크가 불안정하다.** 로딩 스피너가 화면을 차지하면 "오늘 뭐 있지?"에 답을 못 한다 → 6장

## S3. 마감을 통보받은 순간 — 기간형 등록

### Context

- "다음 주 금요일까지 부탁해요"
- 자리에 앉아 있거나 회의 중. 10~20초

### Flow

```
① [+]
② 제목: "3분기 캠페인 보고서"
③ 카테고리: 직장으로 변경 (마지막이 가족이었다면 1탭)
④ [기간으로 설정] 토글 ON  ← 접혀 있던 게 펼쳐짐
⑤ 종료일: 8/14 선택
⑥ [저장]
```

### 인สิ트

- ④의 토글이 **처음부터 펼쳐져 있으면 S1이 느려진다.** 접어두는 게 맞다
- 시작일 기본값은 **오늘**이다. "다음 주 금요일까지"에서 시작은 지금이니까
- 이 순간 하윤이 궁금한 건 **며칠 남았는가**다 → 카드에 `D-11` 또는 "8/14까지" 표기
- "매일 체크" 토글은 ④를 켠 뒤에야 나타난다. 여기선 건드리지 않고 지나간다 (기본 `once`)

---

## S4. "이번 달부터 걷기" — 지속형 등록

### Context

- 마음먹은 순간. 주로 밤이나 주말
- 시간 여유 있음

### Flow

```
① [+] → 제목: "30분 걷기" → 카테고리: 개인
② [기간으로 설정] ON → 종료일 8/31
③ [매일 체크] ON        ← 여기서만 나타나는 토글
④ [저장]

이후 매일:
⑤ 오늘 리스트에서 "30분 걷기" 체크 → completedDates에 오늘 추가
⑥ 카드에 "12/31일" 진행률 갱신
```

### 인사이트

- ③은 **기간형을 켠 뒤에만** 보인다. 2단 접기 (요구사항 4.4.1)
- 지속형은 **매일 리스트에 등장한다.** 8/1~8/31이면 31일 내내 오늘 리스트에 뜬다
  - → 다른 할일을 밀어낼 수 있다. **지속형은 리스트 하단에 모아 배치**하는 게 나을 수 있음 (Phase 5에서 검증)
- 진행률 "12/31일"은 성취감 장치다 → **Phase 4의 재료**
- 어제 체크를 깜빡했으면? **과거 날짜로 이동해 체크할 수 있어야 한다.** 오늘만 체크 가능하면 안 됨

## S5. 퇴근길 지하철 · 색 바꾸기 — 즐거움

### Context

- 앉아서. 두 손. 5~10분 여유
- 목적이 없다. **그냥 앱을 만진다**

### Flow

```
① 오늘 할일 정리 — 못 한 거 내일로 미루기
② 다음 주 훑어보기
③ "가족 색이 좀 칙칙한데" → 카테고리 편집
④ 파스텔 팔레트에서 색 골라보기 — 바꿔보고 되돌리고
⑤ 달력 색이 바뀌는 걸 확인
```

### 인사이트

**S4-c 답변의 무게가 여기 있다.**

- 카테고리 편집은 **설정 화면 3단계 깊이에 있으면 안 된다.** 2탭 이내
- 색 변경은 **즉시 미리보기**돼야 한다. 저장 버튼을 눌러야 결과를 보는 방식이면 "재미"가 사라진다
- 팔레트는 **고를 맛이 나야 한다** — 8~12개의 잘 고른 파스텔. 자유 컬러피커는 오히려 재미가 없다 (선택 부담 + 못생긴 색 나옴)
- 이 시나리오는 **리텐션 장치**다. 목적 없이 앱을 여는 이유가 되기 때문

> 팔레트 디자인은 Phase 5의 **핵심 과제**다. 곁다리가 아니다.

## S6. 자기 전 침대 — 하루 마감

### Context

- 누워서. 한 손. 어두움
- "오늘 뭐 했지 / 내일 뭐 있지"

### Flow

```
① 앱 실행 → 오늘 화면
② 완료된 항목들이 취소선으로 보임 → 오늘의 성과
③ 내일 날짜 탭 → 내일 할일 확인
④ 생각난 거 하나 추가 (날짜 기본값이 내일이어야 함 ← 선택된 날짜 기준)
```

### 인사이트

- **완료 항목이 사라지면 이 시나리오가 죽는다.** "오늘 뭐 했지"에 답할 게 없어짐
  - → `F5-2 완료 항목 숨기기`는 **기본 OFF**여야 한다
- ④가 중요: [+] 의 날짜 기본값은 **오늘이 아니라 "현재 선택된 날짜"**다. 내일을 보다가 추가하면 내일 것
- 어두운 환경 → **다크 모드**가 Out of Scope에 있지만, 이 시나리오가 근거를 만든다. Phase 5에서 재검토

## S7. 배우자 카톡을 받고 — 앱 전환

### Context

- 카톡: "오는 길에 우유 좀"
- 카톡 → 할일 앱 → 카톡 으로 왕복
- **가장 귀찮은 순간.** S5-b(이탈)가 여기서 시작된다

### Flow

```
① 카톡 읽음
② 홈 → 앱 실행 → [+] → "우유" → 저장 → 카톡 복귀
```

### 인사이트

- 앱 전환 비용 때문에 **"그냥 카톡에 놔두지"**가 된다. 이게 S5-b의 실체
- v1에서 할 수 있는 것: **앱 실행 → 입력까지의 경로를 짧게.** PWA로 홈 화면에 설치 가능하게
- v1에서 못 하는 것: 공유 시트 연동, 위젯 — 네이티브 영역
- **v2의 씨앗**: 이 할일은 원래 강민이 직접 적었어야 한다. 가족 카테고리를 공유하면 강민이 "우유"를 직접 넣는다
  - → 공유가 단순한 기능 추가가 아니라 **이 마찰의 근본 해결책**임을 보여준다

## S8. 서지호의 첫 30초 — 게스트

### Context

- 포트폴리오 링크 클릭. 데스크톱 또는 휴대폰
- 기대 없음. 로그인 화면이 나오면 닫는다

### Flow

```
0초   링크 열림 → 로그인 없이 바로 앱 화면
3초   달력 + 파스텔 카테고리 + 오늘 리스트가 한눈에
      → "아, 색으로 영역 나누는 할일 앱이구나"
10초  [+] 눌러 아무거나 하나 추가
20초  체크해봄 → 달력의 점이 흐려지는 걸 봄
25초  카테고리 색 하나 바꿔봄
30초  닫음
```

### 인사이트

- **빈 화면이면 3초 안에 성격 전달이 안 된다.** 첫 실행 시 기본 카테고리 3개(직장·개인·가족)는 반드시 있어야 함
- 할일이 0개면? → 샘플 데이터를 넣을지 말지가 갈린다
  - 넣으면: 서지호는 즉시 이해. 하윤은 첫날 지우는 수고
  - 안 넣으면: 서지호는 빈 달력만 봄
  - **절충**: 할일은 안 넣되, 빈 상태 화면에서 앱의 성격을 문장으로 전달 + [+]로 유도
- 20초의 "체크 → 달력 반영"이 **가장 강한 데모**다. 이 즉각 반응이 느리면 인상이 죽는다
- 튜토리얼 오버레이는 넣지 않는다 (Phase 2 P3 주의사항)

## S9. 역시나리오 — 앱을 안 열게 되는 흐름 ⚠️

**S5-b를 그대로 전개하면 이렇게 된다.**

```
1일차  회의 끝 → 앱 실행 → 로딩 스피너 2초 → [+] → 카테고리 선택 → 날짜 확인 → 저장
       (12초 걸림)

3일차  "아 그냥 카톡에 보내자"  ← 3초

7일차  카톡에 3개, 앱에 2개. 어디에 뭐가 있는지 모름

14일차 앱을 열어봐야 최신이 아님 → 신뢰 상실 → 안 엶
```

### 이탈을 막는 지점

| 시점 | 막는 방법 |
|---|---|
| **1일차 12초** | 기본값 자동 채움, 하단 [+], 즉시 커서 포커스 → **3초** |
| 1일차 로딩 2초 | 캐시 우선 렌더 (6장) |
| 3일차 "카톡이 빠름" | PWA 설치로 실행 경로 단축 |
| 7일차 분산 | — v1에서 해결 불가. v2 공유가 근본 대응 |
| 14일차 신뢰 상실 | 저장 실패를 숨기지 않기 (F6-5) |

## 2. 설계 원칙

시나리오에서 도출된 원칙. 화면 설계·구현 시 이 목록으로 판단한다.

| ID | 원칙 | 근거 |
|---|---|---|
| **P1** | **입력은 3탭·3초.** 제목 외 모든 필드에 기본값이 채워져 있다 | S1, S9 |
| **P2** | 앱을 열면 **항상 오늘**. 마지막 본 날짜를 기억하지 않는다 | S2 |
| **P3** | 달력과 오늘 리스트가 **한 화면에** 보인다 (375px 기준, 스크롤 없이) | S2 |
| **P4** | 주요 조작은 **하단 엄지 영역**에 둔다 | S1 |
| **P5** | 복잡한 선택지는 **접어둔다.** 기간 → 매일체크 2단 접기 | S3, S4 |
| **P6** | [+]의 날짜 기본값은 **선택된 날짜**다 (오늘이 아니라) | S6 |
| **P7** | **완료 항목은 사라지지 않는다.** 숨기기는 기본 OFF | S6 |
| **P8** | 카테고리 색 편집은 **2탭 이내 + 즉시 미리보기** | S5 |
| **P9** | 팔레트는 **엄선된 8~12색.** 자유 컬러피커를 쓰지 않는다 | S5 |
| **P10** | 지속형은 **과거 날짜도 체크 가능**해야 한다 | S4 |
| **P11** | 체크 → 달력 반영은 **즉각**이다. 서버 응답을 기다리지 않는다 | S8, S9 |
| **P12** | 빈 상태에서도 **앱의 성격이 전달**된다. 샘플 할일은 넣지 않는다 | S8 |
| **P13** | 저장 실패를 **숨기지 않는다** | S9 |

## 3. 원칙 간 충돌

### P11(즉각 반영) vs P13(실패를 숨기지 않기)

즉각 반영하려면 서버 응답 전에 화면을 바꿔야 하고(낙관적 UI), 그러면 실패했을 때 화면을 되돌려야 한다.

**해결**: 낙관적 업데이트 + 실패 시 **롤백 + 명시적 알림**.
"저장했습니다" 토스트는 띄우지 않고, **실패했을 때만** 알린다.

### P3(한 화면) vs 카테고리 6개 이상

달력 셀에 점이 많아지면 압축이 무너진다.
**해결**: 셀당 점 최대 3개 + `+N` (Phase 2 T3에서 이미 결정)

## 4. ✅ 해결됨 — 지하철 네트워크

**S2가 요구사항과 충돌했다.**

| | |
|---|---|
| 요구사항 | 로그인 모드는 **Supabase 단일 소스, 온라인 전제** (01-req 2장, Q8-a) |
| S2 현실 | 하윤의 주 사용 시점이 **지하철**이다. 신호가 끊긴다 |
| 결과 | 아침마다 로딩 실패 → S9의 "14일차 신뢰 상실"로 직행 |

### 선택지

| | 방안 | 비용 | 결과 |
|---|---|---|---|
| (가) | 그대로 — 오프라인이면 못 씀 | 0 | 지하철에서 앱이 안 열림. **S2가 성립하지 않음** |
| **(나)** | **읽기 캐시 + 쓰기 재시도 큐** | 반나절 | 마지막 데이터를 즉시 보여주고, 오프라인 입력은 큐에 담아 온라인 시 자동 전송 |
| (다) | 완전한 오프라인 우선 + 충돌 병합 | 1일+ | v1 예산 초과 |

**✅ 결정: (나) 채택.**

개인 1인 사용이라 **동시 편집 충돌이 구조적으로 없다.** 그래서 (다)의 어려운 부분(병합)이 필요 없고,
"마지막 상태를 로컬에 캐시 + 실패한 쓰기를 순서대로 재전송"만으로 충분하다.
게스트 모드용 localStorage 코드가 재활용된다.

상세 규칙 7개는 [`01-requirements.md` 3.5](./01-requirements.md) 참조.

**이 결정이 시나리오에 미치는 영향**

| 시나리오 | 변화 |
|---|---|
| **S2 아침 지하철** | 성립한다. 신호가 없어도 캐시가 즉시 뜨고 체크도 된다 |
| **S1 회의 후 입력** | 로딩 2초가 사라져 3초 목표에 도달 가능 |
| **S9 이탈 경로** | "1일차 로딩 2초"와 "14일차 신뢰 상실" 두 지점이 동시에 막힘 |
| **P11 vs P13 충돌** | 해소. 낙관적 반영 후 실패는 **에러가 아니라 대기 상태**로 처리 |

**새로 생긴 UI 요구**: 대기 중인 변경을 알리는 **조용한 표식**("동기화 대기 N") 하나가 필요하다. → Phase 5에서 위치 결정.
