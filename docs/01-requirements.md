# 01. 요구사항 정의서

> 색으로 구분하는 다중 영역 할일 앱 — 달력 위에서 여러 날짜에 걸친 일정을 관리한다.

작성일: 2026-08-03
문서 위치: `D:\to do app\docs\`
버전: v1 (개인용) — 공유·다중 사용자는 v2

## 1. 프로젝트 개요

### 1.1 한 줄 정의

> 개인이 **직장 / 개인 / 가족** 등 삶의 영역별로 할일을 나누고, 각 영역에 **파스텔 색상**을 지정해
> **월간 달력** 위에서 여러 날에 걸친 일정을 한눈에 파악하는 **모바일 우선** 할일 앱.

### 1.2 목적

| 축 | 내용 |
|---|---|
| **1차 목적** | 포트폴리오 — 채용/외부 공유를 전제로 완성도와 디자인 품질을 갖춘다 |
| **2차 목적** | 실사용 — 만든 사람이 실제로 매일 쓸 수 있어야 한다 |

두 목적이 충돌할 때의 판단 기준:
- **보여주기용 화려함 < 실제로 손이 가는 편의성.** 실사용에서 거슬리는 기능은 포트폴리오에서도 티가 난다.
- 단, **첫인상 3초**(첫 화면의 밀도·색감·정렬)는 포트폴리오 쪽에 무게를 둔다.
- 포트폴리오 목적이 **게스트 모드**(3.1)를 낳았다. 링크를 연 사람이 가입 없이 바로 앱을 만질 수 있어야 한다.

### 1.3 v1 / v2 경계

| | v1 (이번) | v2 (다음) |
|---|---|---|
| 사용자 | 개인 1인 | 다중 사용자 |
| 공유 | 없음 | **카테고리 단위** 공유 |
| 권한 | 없음 | 읽기 전용 / 읽기+쓰기 |
| 편집 주체 | 본인만 | 쓰기 권한자 전원이 추가·수정·삭제 가능 |

**v1에서 v2를 준비하는 방법**: 지금부터 DB 스키마에 `owner_id`와 RLS 정책을 넣어둔다.
v1 동작은 "내 것만 보인다"로 동일하지만, v2에서 테이블을 갈아엎을 필요가 없어진다. (9장 참조)

### 1.4 시간 예산

**하루 반 ~ 이틀.** 인증(이메일+Google) · Supabase 연동 · 게스트 모드 마이그레이션이 포함된 규모다.

### 2.1 반응형 기준 — 모바일 우선

**기본(base) 스타일이 모바일**이고, 미디어 쿼리는 `min-width`로만 확장한다.
`max-width`로 데스크톱 스타일을 되돌리는 방식은 쓰지 않는다.

| 구간 | 폭 | 레이아웃 |
|---|---|---|
| **모바일 (설계 기준)** | 375 ~ 767px | 단일 컬럼. 달력이 상단, 당일 리스트가 그 아래. 추가 버튼은 엄지가 닿는 하단 고정 |
| 태블릿 | 768 ~ 1023px | 달력 셀이 커지고 각 셀에 할일 제목이 직접 보임 |
| 데스크톱 | 1024px ~ | 달력과 리스트를 나란히 배치 (Phase 5에서 확정) |

**모바일 우선이 낳는 파생 결정**
- 달력 셀은 좁으므로 **점(dot) 또는 얇은 막대**로만 표현하고, 제목은 아래 리스트에서 읽는다
- 할일 추가·수정은 화면 전환(모달·바텀시트)으로 처리한다 — 사이드 패널 방식은 모바일에서 성립하지 않음
- 카테고리 필터는 가로 스크롤 칩(chip) 형태를 기본으로 한다
- 터치 타깃 44×44px가 **기본값**이지 예외 처리가 아니다

## 3. 인증과 데이터 모드

### 3.1 두 가지 실행 모드

앱은 **게스트 모드**와 **로그인 모드** 두 상태로 동작한다.

| | 게스트 모드 | 로그인 모드 |
|---|---|---|
| 진입 | 첫 방문 시 기본 | 로그인/가입 후 |
| 저장소 | localStorage | Supabase Postgres (+ 로컬 캐시) |
| 기능 범위 | **할일·카테고리 전 기능 동일** | 동일 + 기기 간 유지 |
| 제약 | 브라우저를 지우면 사라짐 | 첫 로그인 시에는 온라인 필요 |
| 오프라인 | 완전 동작 | 읽기·쓰기 모두 동작 (3.5) |

**게스트 모드에서도 기능을 깎지 않는다.** 포트폴리오 방문자가 보는 화면이 반쪽이면 의미가 없다.
대신 화면 어딘가에 "로그인하면 다른 기기에서도 이어서 쓸 수 있어요" 수준의 조용한 안내를 둔다.

### 3.2 로그인 방식

| 방식 | 상세 |
|---|---|
| 이메일 + 비밀번호 | 가입 · 로그인 · 로그아웃. 이메일 인증 메일 발송 |
| Google 소셜 | Supabase OAuth. Google Cloud Console에서 OAuth 클라이언트 ID 발급 필요 |

**비밀번호 재설정**은 v1 범위에 포함한다. (없으면 실사용이 안 됨)

### 3.3 게스트 → 로그인 데이터 이관

게스트로 쓰던 데이터가 로그인 순간 사라지면 안 된다.

```
게스트로 사용 중 (localStorage에 데이터 있음)
        │
        ▼  로그인 / 가입
"이 기기에 저장된 할일 N개가 있어요. 계정으로 가져올까요?"
        │
   ┌────┴────┐
   ▼         ▼
 가져오기   그냥 두기
   │         └─ localStorage 데이터는 남기고 계정 데이터만 사용
   ▼
Supabase에 업로드 → 성공하면 localStorage 비움
```

**이관 규칙**
- 이미 계정에 데이터가 있으면 **덮어쓰지 않고 병합**한다 (게스트 데이터를 추가로 얹음)
- 카테고리 이름이 겹치면 **기존 계정 카테고리로 합친다** (새로 만들지 않음)
- 업로드 도중 실패하면 localStorage 데이터를 **지우지 않는다**
- 이관은 **한 번만** 묻는다. "그냥 두기"를 고르면 다시 묻지 않는다

### 3.4 로그아웃

로그아웃하면 게스트 모드로 돌아간다. 계정 데이터는 서버에 남고, 화면에서는 보이지 않는다.
로그아웃 시 **로컬 캐시와 재시도 큐를 모두 비운다.** 남의 기기에 데이터가 남으면 안 된다.
단, 큐에 전송되지 않은 항목이 있으면 **로그아웃 전에 경고**한다.

### 3.5 오프라인 대응 — 캐시 우선 + 재시도 큐

주 사용 시점이 **지하철**(03-scenarios S2)이라 온라인을 전제할 수 없다.
다만 **완전한 오프라인 우선 아키텍처는 만들지 않는다.** 개인 1인 사용이라 동시 편집 충돌이 구조적으로 없기 때문에, 어려운 부분(병합 알고리즘)은 통째로 생략된다.

```
읽기:  로컬 캐시를 즉시 렌더  →  백그라운드로 서버 조회  →  차이가 있으면 갱신
쓰기:  화면을 먼저 바꿈(낙관적)  →  서버 전송
                                    ├ 성공 → 끝
                                    └ 실패 → 재시도 큐에 적재 + 화면에 '대기 중' 표시
온라인 복귀:  큐를 순서대로 재전송
```

**규칙**

| # | 규칙 |
|---|---|
| 1 | 앱 시작 시 **로딩 스피너로 화면을 막지 않는다.** 캐시가 있으면 즉시 보여준다 |
| 2 | 쓰기는 항상 **낙관적 반영**. 서버 응답을 기다리지 않는다 |
| 3 | 전송 실패는 **에러가 아니라 대기 상태**다. 사용자에게 재입력을 요구하지 않는다 |
| 4 | 큐는 **순서를 지켜** 재전송한다 (생성 → 수정 → 삭제 순서가 뒤집히면 안 됨) |
| 5 | 재전송이 **최종 실패**하면(4xx 등) 그때는 명시적으로 알리고 화면을 되돌린다 |
| 6 | 큐에 대기 중인 항목이 있으면 UI에 **조용한 표식** 하나를 둔다 ("동기화 대기 N") |
| 7 | 같은 항목을 여러 번 수정하면 큐에서 **합친다** (마지막 상태만 전송) |

**서버 데이터와 캐시가 다르면?**
서버가 이긴다. 단 **큐에 대기 중인 로컬 변경은 예외** — 큐를 먼저 비운 뒤 서버 상태를 받는다.

**충돌 처리는 만들지 않는다.**
다른 기기에서 동시에 편집하는 상황은 v1 범위 밖이다. 마지막 쓰기가 이긴다(last-write-wins).
v2에서 공유가 들어오면 이 결정을 재검토해야 한다.

## 4. 데이터 모델

### 4.1 DB 스키마 (Supabase / Postgres)

```sql
-- 카테고리
create table categories (
  id          uuid primary key default gen_random_uuid(),
  owner_id    uuid not null references auth.users(id) on delete cascade,
  name        text not null,
  color       text not null,          -- 파스텔 색상 hex
  sort_order  int  not null default 0,
  created_at  timestamptz not null default now()
);

-- 할일
create table tasks (
  id              uuid primary key default gen_random_uuid(),
  owner_id        uuid not null references auth.users(id) on delete cascade,
  category_id     uuid references categories(id) on delete set null,  -- null = 미분류
  title           text not null,
  memo            text,
  start_date      date not null,
  end_date        date not null,
  check_mode      text not null default 'once'
                    check (check_mode in ('once', 'daily')),
  done            boolean not null default false,   -- check_mode='once' 일 때만 의미
  completed_dates date[]  not null default '{}',    -- check_mode='daily' 일 때만 의미
  sort_order      int  not null default 0,
  created_at      timestamptz not null default now(),
  constraint valid_range check (end_date >= start_date)
);
```

**설계 의도 세 가지**

1. `category_id ... on delete set null` — 카테고리를 지워도 할일은 살아남고 `null`(미분류)이 된다. 삭제 정책(4.3)이 DB 레벨에서 보장된다.
2. `owner_id` — v1에서는 항상 본인 id지만, v2에서 `category_shares` 테이블을 추가하면 RLS 정책만 고쳐 공유를 켤 수 있다.
3. `check_mode` — 하나의 테이블로 **마감형**과 **지속형**을 모두 표현한다. 별도 테이블이나 반복 규칙 엔진 없이 컬럼 두 개로 끝낸다. (4.4 참조)

### 4.2 RLS 정책 (v1)

모든 테이블에 RLS를 켜고, 본인 소유 행만 접근 가능하게 한다.

```sql
alter table categories enable row level security;
alter table tasks      enable row level security;

create policy "own categories" on categories
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy "own tasks" on tasks
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());
```

> v2에서는 이 정책에 `or exists (select 1 from category_shares ...)` 를 더하는 것으로 공유가 열린다.

### 4.3 카테고리 삭제 정책

카테고리는 **소속 할일이 있어도 삭제할 수 있다.** 삭제 자체를 막지 않는다.

| 상황 | 동작 |
|---|---|
| 소속 할일 0개 | 확인 없이 바로 삭제 |
| 소속 할일 1개 이상 | 확인 다이얼로그에서 선택<br>① **할일은 "미분류"로 옮기고 카테고리만 삭제** (기본)<br>② **할일까지 함께 삭제** (되돌릴 수 없음을 명시) |

- `미분류`는 실제 레코드가 아니라 **`category_id IS NULL` 을 화면에서 부르는 이름**이다. 이름변경·삭제 대상이 아니다.
- 미분류 할일이 0개면 UI에 노출하지 않는다.
- 마지막 남은 카테고리도 삭제할 수 있으며, 그 경우 "카테고리를 만들어주세요" 빈 상태가 된다.

### 4.4 클라이언트 타입

```ts
interface Category {
  id: string;
  name: string;        // "직장", "개인", "가족" — 수정 가능
  color: string;       // 파스텔 hex — 사용자가 선택
  sortOrder: number;
}

type CheckMode = 'once' | 'daily';

interface Task {
  id: string;
  categoryId: string | null;   // null = 미분류
  title: string;
  memo?: string;
  startDate: string;           // "YYYY-MM-DD"
  endDate: string;             // "YYYY-MM-DD" — 하루짜리면 startDate와 동일
  checkMode: CheckMode;
  done: boolean;               // checkMode='once' 전용
  completedDates: string[];    // checkMode='daily' 전용. ["2026-03-01", ...]
  sortOrder: number;
  createdAt: string;
}
```

### 4.4.1 핵심 설계 판단 — 기간형 + 두 가지 체크 방식

할일은 `startDate ~ endDate` 기간을 가진다. 그 기간을 **어떻게 완료 처리할지**가 두 갈래다.

| | `once` — 마감형 (기본) | `daily` — 지속형 |
|---|---|---|
| 표현 | `"이사 준비" 3/10 ▓▓▓▓▓▓▓ 3/16` | `"매일 걷기" 3/1☑ 3/2☑ 3/3☐ 3/4☐` |
| 체크 | 기간 전체에 **한 번** | **날짜마다** 따로 |
| 저장 | `done: boolean` | `completedDates: string[]` |
| 완료 판정 | `done === true` | 기간 내 모든 날짜가 `completedDates`에 있음 |
| 진행률 | 없음 | `12 / 31일` 형태로 표시 |
| 쓰이는 곳 | 업무 마감, 이벤트 준비 | 운동·복약·습관 |

**규칙**
- **하루짜리 할일(`startDate === endDate`)은 항상 `once`.** 지속형 선택지를 노출하지 않는다
- 기간형으로 설정할 때만 "매일 체크" 토글이 나타난다. **기본값은 `once`**
- `checkMode`를 `daily` → `once`로 바꾸면 `completedDates`는 **지우지 않고 보관**한다 (되돌리면 복원)
- `once` → `daily`로 바꾸면 `done`은 무시되고 `completedDates`가 빈 배열에서 시작

**채택하지 않은 것**
규칙 기반 반복(“매주 화·목”, “격주”)은 v1 범위 밖이다. 지속형은 **연속된 기간의 날짜별 체크**까지만 지원한다.

### 4.4.2 기간형 공통 파생 규칙

- `endDate >= startDate` 를 DB 제약과 입력 검증 양쪽에서 보장한다
- 기간이 달을 넘어가면(3/28 ~ 4/3) 양쪽 달의 달력에 모두 표시된다
- 완료된 할일도 달력에서 사라지지 않고 **흐리게 + 취소선**으로 남는다
- 지속형은 **오늘 날짜의 체크 여부**가 달력·리스트에서 우선 표현된다 (전체 완료보다 "오늘 했나"가 중요)

### 4.5 게스트 모드 저장 구조

localStorage 키 하나에 아래를 JSON으로 저장한다. 스키마 버전 필드를 둔다.

```ts
interface GuestData {
  schemaVersion: number;
  categories: Category[];
  tasks: Task[];
  migrationAsked: boolean;   // 3.3의 "한 번만 묻는다"
}
```

초기 카테고리 3개(**직장 / 개인 / 가족**)는 게스트·로그인 양쪽에서 최초 1회 생성한다.

## 6. 비기능 요구사항

### 6.1 성능

- 할일 300개 기준으로 달력 전환·체크 토글이 체감 지연 없이 동작
- 초기 로딩 2초 이내 (네트워크 포함)
- 달력은 표시 중인 달 ± 여유 범위만 조회한다 (전체 조회 금지)

### 6.2 접근성

- 모든 인터랙티브 요소에 키보드 접근 가능
- 체크박스·버튼에 적절한 label / aria 속성
- **색만으로 카테고리를 구분하지 않는다 (확정)** — 파스텔 배경은 채도가 낮아 색각 이상 사용자에게 구분이 어렵다. 할일 카드에 카테고리 **이름 텍스트를 항상 함께 노출**한다. 공간이 좁은 모바일에서도 생략하지 않는다
- 텍스트 대비: 파스텔 배경 위 본문 텍스트가 WCAG AA(4.5:1)를 만족하도록 색을 고른다

### 6.3 반응형 (모바일 우선)

- **375px(iPhone SE)를 설계 기준 폭으로 삼는다**
- 모든 터치 타깃 최소 44×44px
- 어떤 폭에서도 가로 스크롤이 발생하지 않음
- 주요 조작(추가·체크·날짜 이동)이 한 손 엄지 범위 안에서 가능

### 6.4 한글 입력

- 한글 IME 조합 중 Enter가 중복 입력되지 않도록 처리 (`isComposing` 확인)

### 6.5 보안

- Supabase **anon key만** 클라이언트에 노출한다. service role key는 절대 클라이언트로 나가지 않는다
- 모든 테이블에 RLS를 켠다. RLS 없이 배포하지 않는다
- `.env.local`은 `.gitignore`에 포함하고 `.env.example`만 커밋한다

## 9. v2 로드맵 — 공유와 권한

v1 구현 시 아래를 염두에 둔다. **지금 만들지는 않는다.**

```sql
-- v2에서 추가될 테이블 (예정)
create table category_shares (
  category_id uuid references categories(id) on delete cascade,
  user_id     uuid references auth.users(id) on delete cascade,
  permission  text not null check (permission in ('read', 'write')),
  primary key (category_id, user_id)
);
```

| v2 요구사항 | 메모 |
|---|---|
| 카테고리 단위 공유 | 할일 단위가 아니라 카테고리 통째로 |
| 읽기 / 읽기+쓰기 권한 | |
| 쓰기 권한자 전원이 수정·삭제 가능 | 작성자만 수정 같은 제한 없음 |
| 소유자 개념 | 카테고리 삭제·권한 변경은 소유자만 — v2 진입 시 재확인 필요 |
| 초대 방식 | 이메일 초대 / 링크 / 코드 — v2 진입 시 결정 |
| 실시간 반영 | Supabase Realtime 검토 |

**v1이 v2를 막지 않기 위한 조건**
- 모든 조회를 `owner_id = auth.uid()` 하드코딩이 아니라 **RLS에 위임**한다. 그래야 정책만 고쳐 공유가 열린다
- 클라이언트 코드에서 "이건 내 것"이라는 가정을 UI 분기에 박아넣지 않는다
