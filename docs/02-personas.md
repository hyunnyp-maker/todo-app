## 0. 이 문서가 하는 일

페르소나는 "누가 쓰나"를 적는 문서가 아니다.
**설계 판단이 갈릴 때 누구 편을 들 것인지** 미리 정해두는 문서다.

이 앱에는 세 명이 등장한다.

| | 인물 | 역할 |
|---|---|---|
| **P1** | 정하윤 (35) | **주 페르소나.** 매일 쓰는 사람. 충돌 시 이 사람 편 |
| **P2** | 강민 (37) | **대조 페르소나.** v1에서는 쓸 수 없는 사람. v2의 존재 이유 |
| **P3** | 서지호 (41) | **관문 페르소나.** 30초만 보고 떠나는 사람. 첫인상의 기준 |

## 1. P1 — 정하윤 (35) · 주 페르소나

> "회의 끝나고 나오면서 '어린이집 준비물' 생각났는데, 자리 앉으면 까먹어요."

### 프로필

| | |
|---|---|
| 나이 · 직업 | 35세 · 중견기업 마케팅팀 |
| 가족 | 배우자 1, 자녀 1 (6세) |
| 기기 | 출퇴근·회사에서는 **휴대폰**, 주말 계획은 가끔 노트북 |
| 하루 구조 | 출근 → 회의·업무 → 퇴근 → 육아 → 밤 30분의 개인 시간 |

### 하루에 섞이는 세 영역

이 사람의 하루는 카테고리 3개가 **시간 순서대로 분리되지 않는다.** 뒤섞인다.

```
09:00  ▓직장  주간 보고서 초안
11:30  ▓가족  어린이집 준비물 챙기기      ← 회의 중에 생각남
14:00  ▓직장  캠페인 예산 검토
18:40  ▓가족  장보기
22:00  ▓개인  건강검진 예약
```

**이 뒤섞임이 색 구분의 존재 이유다.** 시간대로는 나뉘지 않으니, 시각적으로 나뉘어야 한다.

### 목표

1. 생각난 순간 3초 안에 적어놓기 — 안 적으면 사라진다
2. 지금 이 순간 뭘 해야 하는지 한 화면에서 파악
3. 여러 날 걸리는 일이 **언제 끝나야 하는지** 놓치지 않기
4. 체크하는 맛 — 하루 끝에 "오늘 뭘 했지"가 눈에 보이기

### 불만 (= 이 앱의 존재 이유)

**P3-b. 기본 캘린더 앱 — 일정은 되는데 완료 개념이 없다**

> "캘린더에 '보고서 마감' 넣어놨는데, 그거 끝냈는지 아닌지가 캘린더엔 안 남아요.
> 지난 주 화면을 봐도 그게 한 일인지 못 한 일인지 모르겠어요."

- 캘린더는 **시간의 도구**지 **완료의 도구**가 아니다
- 일정을 지우면 기록이 사라지고, 안 지우면 완료 여부를 알 수 없다

**P3-c. 노션 / Todoist — 기능은 많은데 무겁고 열기 귀찮다**

> "노션은 열면 로딩이 있고, 어느 페이지에 적었는지부터 찾아야 해요.
> 회의 나오면서 30초 안에 적어야 하는데 그 30초를 앱 여는 데 씁니다."

- 진입 비용이 기록 행위 자체보다 크다
- 기능이 많다는 건 **결정할 게 많다**는 뜻 — 프로젝트? 태그? 우선순위? 정하다가 안 적게 된다

### 이 두 불만이 합쳐지면

> **"캘린더의 날짜 감각 + 할일 앱의 체크. 그런데 노션보다 가벼울 것."**

이게 이 앱의 한 줄 정체성이다.

### 행동 패턴

- **하루 여러 번, 짧게 연다** (P2-b). 한 번에 5초~30초
- 추가는 **생각난 순간**에 일어난다 — 자리에 앉아서가 아니라 걸으면서, 서서
- 확인은 **아침·점심 직후·퇴근 직전** 세 번이 몰림
- 계획을 미리 짜지 않는다. 들어오는 대로 쌓고, 날짜를 나중에 맞춘다

### 여러 날 할일의 실제 모습 (P4-a·b·c 전부)

| 유형 | 예시 | 이 사람에게 중요한 것 |
|---|---|---|
| **업무 마감형** | "3분기 캠페인 보고서 3/10~3/14" | **끝나는 날.** 며칠 남았는지 |
| **준비형** | "제주 여행 준비 4/1~4/12" | **시작했다는 감각.** 남은 기간 안에 뭘 해야 하는지 |
| **지속형** | "매일 30분 걷기 3/1~3/31" | **오늘 했는지.** 며칠 연속인지 |

> ⚠️ **세 번째 유형이 v1 데이터 모델과 충돌한다.** 5장에서 다룬다.

## 2. P2 — 강민 (37) · 대조 페르소나

> "하윤 씨가 다 알아서 하는데, 나는 뭘 해야 하는지 물어봐야 알아요."

### 프로필

| | |
|---|---|
| 관계 | P1의 배우자 |
| 기기 | 휴대폰만 |
| 앱 태도 | 새 앱 설치를 귀찮아함. 기존 것도 잘 안 씀 |

### 원하는 것

- **가족 일정만** 보고 싶다. 하윤의 직장 업무나 개인 일정에는 관심도 없고 봐서도 안 된다
- 편집은 거의 안 한다. "장보기 내가 할게" 정도로 **가끔** 체크만 하고 싶다
- 앱을 새로 배우고 싶지 않다

### 이 사람이 던지는 설계 요구

| 요구 | v1에서의 대응 |
|---|---|
| 카테고리 **단위**로만 공유 (할일 하나씩이 아니라) | 스키마를 `category_id` 중심으로 설계 — 이미 반영됨 |
| **읽기 전용** 권한이 실재해야 함 | v2. 지금은 RLS 정책만 확장 가능하게 열어둠 |
| 남의 다른 카테고리는 **보여서도 안 됨** | RLS로 강제. 클라이언트 필터링에 의존하지 않음 |
| 가입 부담이 최소여야 함 | Google 로그인 제공 |

### v1에서 이 사람의 자리

**없다.** 강민은 v1을 쓸 수 없다.

이걸 문서에 남기는 이유는, **v1의 모든 결정이 강민을 나중에 받아들일 수 있어야** 하기 때문이다.
"어차피 혼자 쓰니까"라며 `owner_id`를 빼거나 조회를 하드코딩하면, v2에서 전부 다시 만들게 된다.

> **강민은 v1의 사용자가 아니라 v1의 제약 조건이다.**

## 3. P3 — 서지호 (41) · 관문 페르소나

> (링크 클릭) "음… 로그인 화면이네." (닫기)

### 프로필

| | |
|---|---|
| 역할 | 채용 담당자 / 개발팀 리드 |
| 이 앱과의 접점 | 포트폴리오 링크를 **한 번** 클릭 |
| 체류 시간 | **30초~2분** |
| 기기 | 데스크톱이 많지만 휴대폰으로 여는 경우도 흔함 |

### 행동 순서

```
링크 클릭 → 첫 화면 3초 → (흥미 있으면) 할일 하나 추가 → 체크 → 색 바꿔보기 → 끝
```

### 이 사람이 던지는 설계 요구

| 요구 | 대응 |
|---|---|
| **가입 없이** 즉시 만질 수 있어야 함 | 게스트 모드 (요구사항 3.1) |
| 빈 화면이면 뭘 하는 앱인지 모름 | 첫 실행 시 기본 카테고리 3개 + 빈 상태 안내 |
| 30초 안에 앱의 **성격**이 전달돼야 함 | 달력 + 파스텔 색 구분이 첫 화면에 동시에 보여야 함 |
| 휴대폰으로 열어도 깨지지 않아야 함 | 모바일 우선 |

### 주의

**서지호를 위해 P1의 경험을 희생하지 않는다.**
튜토리얼 오버레이, 화려한 온보딩, 샘플 데이터 잔뜩 — 이런 건 서지호에게 1점을 주고 하윤에게 매일 -1점을 준다.
"가입 없이 열리고, 첫 화면이 이미 설명"이면 충분하다.

## 5. 도출되는 설계 긴장점

### T1. "빠른 추가" vs "여러 날 기간 입력"

하윤은 **3초 안에** 적고 싶은데, 기간형 할일은 시작일·종료일 **두 개**를 입력해야 한다.
입력 필드가 늘어날수록 3초는 지켜지지 않는다.

**해결 방향**
- 기본값은 **선택된 날짜 하루** (시작일=종료일). 대부분의 할일은 하루짜리다
- 여러 날은 **명시적으로 펼쳐야** 나오는 선택지로 둔다 — "기간으로 설정" 토글
- 제목 입력 + 저장만으로 완결되게 한다. 카테고리도 **마지막 선택 카테고리를 기본값**으로

> 원칙: **하루짜리 할일이 기본, 기간은 예외.** 반대로 만들면 매일 쓰는 사람이 손해 본다.

---

### T2. ⭐ "지속형 할일" vs 단일 체크 모델 — **해결됨: (나) 채택**

하윤은 P4에서 **(c) 지속 관리**를 골랐다. "매일 30분 걷기", "약 복용" 같은 것.
그런데 v1 데이터 모델은 **기간 전체에 체크 한 번**이다.

```
현재 모델:  "매일 30분 걷기  3/1 ▓▓▓▓▓▓▓▓▓▓ 3/31"  → ☐ 체크 한 번
필요한 것:  "매일 30분 걷기  3/1☑ 3/2☑ 3/3☐ 3/4☐ ..."  → 날짜마다 체크
```

**이건 요구사항 단계에서 제외한 "반복형"이다.** (01-requirements.md 7장)

세 가지 선택지가 있다:

| | 방안 | 비용 | 결과 |
|---|---|---|---|
| **(가)** | v1은 그대로 두고 **지속형은 포기** | 0 | 하윤이 "걷기"는 이 앱에 안 적게 됨. 앱 밖으로 새는 영역이 생김 |
| **(나)** | `completedDates: string[]` 필드 하나 추가 — 기간형 할일에 **날짜별 체크**를 허용 | 소 (반나절) | 세 유형 모두 수용. 달력에 진행률(12/31일) 표시 가능 |
| **(다)** | 본격 반복 일정(매주 화·목 등 규칙 기반) | 대 (1일+) | v1 예산 초과 |

**✅ 결정: (나) 채택.**

`tasks` 테이블에 `check_mode`와 `completed_dates` 두 컬럼을 더해,
하나의 모델로 마감형과 지속형을 모두 표현한다. 규칙 기반 반복(다)까지는 가지 않는다.

```
once  (기본) : "이사 준비"   3/10 ▓▓▓▓▓▓▓ 3/16   → 체크 1회
daily        : "매일 걷기"   3/1☑ 3/2☑ 3/3☐ ...  → 날짜마다 · 12/31일
```

상세 규칙은 [`01-requirements.md` 4.4.1](./01-requirements.md) 참조.

**하윤에게 미치는 영향**
- P4에서 고른 세 유형(업무 마감 / 이벤트 준비 / 지속 관리)이 **모두 이 앱 안에 들어온다.** 앱 밖으로 새는 영역이 없어짐
- 대신 입력 화면에 토글이 하나 늘었다 → **T1(3초 입력)과 직접 충돌.** "기간으로 설정"을 켰을 때만 "매일 체크"가 나타나는 2단 접기로 완화한다

---

### T3. "모든 카테고리 동시 표시" vs 모바일 좁은 셀

하윤은 모든 카테고리를 한 번에 보길 원하고(B5-a), 화면은 375px다.
카테고리가 3개일 땐 괜찮지만 **6개가 되면** 달력 셀 안의 점이 뭉개진다.

**해결 방향**
- 달력 셀에는 **최대 3개까지 점**을 찍고 나머지는 `+N`
- 점의 순서는 카테고리 `sortOrder` 고정 — 매번 바뀌면 시각적 기억이 안 생김
- **완료된 할일의 점은 옅게.** 색은 유지하되 채도를 낮춤

---

### T4. 하윤의 애착 vs 서지호의 무관심

같은 데이터에 대해 하윤은 **잃으면 큰일**이고, 서지호는 **아무래도 상관없다**.
게스트 모드는 서지호를 위한 것이지만, 하윤도 로그인 전엔 게스트다.

**해결 방향**
- 게스트 데이터를 **함부로 지우지 않는다.** 이관 실패 시 로컬 보존 (요구사항 3.3)
- "로그인하면 다른 기기에서도 이어집니다" 안내는 **조용하게, 상시가 아니라 데이터가 쌓인 뒤에**
- 서지호에게 로그인을 강요하지 않고, 하윤에게 로그인을 잊게 하지 않는다

---

### T5. 강민의 부재가 만드는 규율

v1에는 강민이 없다. 그래서 **"어차피 나 혼자니까"**라는 지름길이 계속 유혹한다.

**금지 사항 (v1 구현 시)**
- ❌ `owner_id` 생략
- ❌ 클라이언트에서 `.eq('owner_id', myId)` 하드코딩 — RLS에 맡긴다
- ❌ 카테고리를 상수 배열로 고정
- ❌ "내 것이니까 당연히 수정 가능"을 UI 분기에 박아넣기

## 6. 우선순위 원칙

설계 판단이 갈릴 때 이 순서로 결정한다.

```
1. 하윤이 매일 3초 안에 적을 수 있는가?        (P1 · 최우선)
2. 강민을 나중에 받아들일 수 있는 구조인가?     (P2 · 구조적 제약)
3. 서지호가 30초 안에 이해하는가?              (P3 · 첫인상)
```

**1번과 3번이 충돌하면 1번이 이긴다.**
매일 쓰는 사람의 마찰은 누적되고, 한 번 보는 사람의 감상은 누적되지 않는다.
